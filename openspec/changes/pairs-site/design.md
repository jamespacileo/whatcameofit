# Design

## Context

- The lab's page models are Pydantic models in `thenwhat-lab` `src/lab/models/production/pages.py`. Each names its `route`. On the lab's branch for step S9 the pair path has `PairPage`, `PairDataFile`, `PairInterventionPage`, `PairTopicsPage`, `PairTopicPage`, `PairClinicalCategoryPage`, `PairChangesFeed` and `LookupIndex`, with `ConditionPage` and `HomePage` declared.
- `lab.page_files.write` writes `<folder>/<page>/<key>.json` and `<folder>/schemas/<Model>.json`, and removes the file of a page no longer made.
- A field marked `Private()` in the lab cannot be reached by a page model: the lab's diagram check refuses it. So a bundle holds public records only.
- The site today: Astro static build, one Worker (`site/worker/index.mjs`) in front of the built files, which answers `/api/lookup` and 410 for archived claims. KV `LOOKUP_RESULTS` exists. D1 databases `thenwhat-store` and `thenwhat-store-preview` exist in the EU jurisdiction, with the store's schema applied by `store/ingest/migrations`.
- Not measured yet: how many pair pages a full run makes, and Cloudflare's present limit on files in one deployment. Both are read before decision 2's line is fixed (task 1.3).

## Decisions

1. **The bundle is the contract, and the lab's schemas are its definition.** The site keeps no schema of its own. At build, `site/scripts` reads `schemas/*.json` from the bundle and writes TypeScript types and compiled validators (no runtime `eval`, so they also run in the Worker). Alternative: a hand-kept `export.schema.json` as today. Rejected: two definitions drift, and the lab's models already fail its own checks when a page changes.
2. **Superseded 2026-11-20 by option (i) below: no pair page is built ahead** (task 4.6b). As first approved: **which pair pages are built ahead is a rule over the bundle, in one tested function.** Built ahead: a pair with a claim origin, or with more than one supporting trial. Every other published pair is rendered on request. The rule's second half is provisional until the rehearsal's count is known; if every pair fits a build of a few minutes and the file limit, all are built ahead and the on-request path stays for pairs published between builds. Approved by the operator on 2026-11-19.

   **Chosen 2026-11-20 (task 1.3): option (i), every pair file on request**, on the cost research the operator asked for (a daily full crawl comes to about 1.35 million requests a month on Workers Paid), under his rule of proceeding on reversible, evidence-backed steps. What follows was the proposal. The operator asked for the leanest design rather than a higher file limit, and on 2026-11-20 decided that legacy claims are removed from the site (their verified 301s kept, other old claim addresses answering 410). Measured on the rehearsal (3,825 pairs): the pair side is 6,116 files (3,834 listing pages; 326 built-ahead pairs at seven files each: page, data file, three cards, embed, oEmbed), the site's own pages and build assets about 130. Search: Pagefind indexes only pages marked `data-pagefind-body`, which were the claim pages alone; with them gone it would index every built page, so a pairs build drops it and the lookup box answers from `lookup.json` (2.56 MB for 3,825 pairs, 214 KB compressed; about 20 MB at 30,000 pairs, under the 25 MiB a file).

   | Option | Rehearsal | About 30,000 pairs |
   | --- | --- | --- |
   | (i) every pair file on request: static only for the site's own pages and the top-level indexes | about 150 | about 150 |
   | (iii-b) built-ahead pairs with one card instead of three, listing pages on request | about 1,780 | about 12,900 |
   | (iii) built-ahead pairs as now, listing pages on request | about 2,430 | about 18,050 |
   | (iv) as built today, without claims | about 6,250 | about 48,100 |

   Cost of a page made on request, measured. D1 (thenwhat-store-preview, rehearsal bundle): a pair page is one keyed read, median 0.5 ms and 2 rows read (the largest, 1.29 MB, 8 to 11 ms and 86 rows); a listing from the lab's page file by key, under 1 ms and 6 rows for an intervention, 14 to 24 ms and 170 rows for the largest category (1,069 pairs); joining the same intervention listing from the row tables reads 3,845 rows, so listings read the page files. CPU per render in V8 (parse, compiled check, view, render): 0.06 ms for a typical pair page, 2.6 ms for the largest, 3.0 ms for the largest category listing, plus the runtime's own per-request time. Time to first byte from a browser on a live preview: 116 ms for the Worker's uncached path to D1, 127 ms for a static built pair page (the Worker runs first for every path in this configuration, so built pages are Worker requests too: "Requests to static assets are free and unlimited", but paths matching `run_worker_first` "will always invoke your Worker script"). The Cache API does not replicate outside the data centre that filled it.

   A crawl of about 30,000 pair and 30,000 listing addresses, each once and uncached in a day, is 60,000 invocations (1.8 million a month if daily, of the 10 million Workers Paid includes), about 60,000 to 180,000 CPU ms (of 30 million a month) and under 5 million D1 rows read (of 25 billion a month): within the included amounts even if repeated daily from ten data centres (Workers and D1 pricing pages, read 2026-11-20, `docs/sources.md`). Of what building ahead bought, crawlers and first paint are covered by the same HTML made on request and a sitemap of every address; share cards are not, since a card is drawn at build: on request it needs drawing in the Worker (resvg as WebAssembly, cached) or the site's own card.

   Being built in small pull requests behind `PAIRS_BUNDLE` (tasks 4.6 onward). Recommended, and chosen: (i), share cards drawn in the Worker and cached (the site's card meanwhile), and `run_worker_first` narrowed to the paths the Worker must answer so every other page is a free static asset. The condition page needs either a `ConditionPage` file from the lab or a table of MeSH tree numbers in D1. The operator picks the option, the cards, and the condition source.
3. **On request, the Worker reads the pair's file from D1** (`pair_page`, by the bundle version the build recorded, model and address, its parts joined in order), validates it with the compiled validator, renders it with the same renderer as a built page, and caches the answer a day under a key that holds the bundle version. A new version therefore needs no purge. An address the bundle does not hold answers the not-found page; a file that fails its validator answers the error page with nothing of the file. Revised by the assistant on 2026-11-20, replacing "the same Astro component (the Cloudflare adapter, that route alone not prerendered)": one plain renderer (`site/src/lib/pair-render.ts`, every value from a file HTML-escaped) writes the page's content for both the built page and the Worker, which fills a frame the build leaves at `/pair-shell` (as the trial reader already does). The two are the same by construction and no adapter is added. The pair path is a Worker entry of its own (`site/worker/with-pairs.mjs`) that only a deployment given a `PAIRS` D1 binding uses; production keeps `worker/index.mjs` until the cutover.
4. **One current version, in the store.** `pair_bundle.current` marks it. The build reads it once and writes the version into the built site, so built pages and on-request pages of one deployment read one version. Loading a bundle does not change a deployed site until the next deployment; `make deploy` is still the only way to publish. The load keeps the current version and the one before, so the deployment before can still be served and deployed again.
5. **Addresses.** A pair page is at `/{address}`, where a claim page was, not under `/pairs/`: the lab's `/pairs/...` routes exist only while its claim path stands beside it. The bundle's redirects file maps each claim slug to its pair's address; where the two are equal no redirect is written. The Worker answers a moved slug 301, an archived one 410 as today.
6. **The first version shows no reports.** Approved by the operator on 2026-11-19. The pages and feeds that need a first report are removed, not hidden behind a flag, and return when the lab's milestone C gives the bundle `ReportRow`s.
7. **Scores and reasons stay visible.** A pair's intervention keyed by the lab's chooser, and any trial matched below the sure band, shows its score and that no person checked it, as `docs/adr/0001` and `0004` require. `checked_by_person` is on `PairPage`.
8. **`lookup.json` is built by the site from the pair pages**, in its own wording, with the keys the released extension reads; its `claims` map is keyed by the pair's address. Decided by the assistant on 2026-11-19, replacing "`lookup.json` is a bundle file (`LookupIndex`), copied to its address by the build": the small bundle holds no `LookupIndex`, and the standing rule is that the site owns all wording while files carry codes. Easy to undo if the lab's file is wanted. The extension's own `stateFor` runs against the built file in the site's build test before the cutover.
9. **Tests.** A bundle of about 50 pages is cut from the lab's eval slice by the lab's bundle command and committed under `site/tests/bundle/`: real page files, no article text (the bundle holds none). `*.test.mjs` cover the rule of decision 2, the redirects and the validators; `*.build-test.mjs` build the small bundle. No test reads D1 itself: the store's tests use its local engine.
10. **Cutover and rollback.** The cutover is one deployment. Rollback is `make deploy` of the previous commit, which still reads the committed claims export. `site/data/published-export.json` is removed from the repository one week after the cutover, not with it.

11. **D1 holds the bundle, in the store's own database** (operator, 2026-11-19; R2 was the first proposal). Migration `0011_pairs.sql` adds `pair_bundle`, `pair_page` and the row tables `pair`, `pair_intervention`, `pair_intervention_name`, `pair_condition`, `pair_trial`, `pair_trial_facts`, `pair_status_change`, every row under its bundle's version. The tables are a read model: written only by `store/ingest/scripts/load-pairs.mjs` from the lab's page files, through `wrangler d1 execute --file`, never through the merge path, and never read back by the lab. The row tables are derived from the `PairPage` files alone, so the lab's models stay the one definition. A page file longer than a statement may be (100,000 bytes) is kept in parts. The claims tables of the store stay as they are until the cutover.
12. **The build reads D1 through an export of the current version**, as `store-export-rehearsal` already does with `wrangler d1 execute --remote --json`, written to disk as the bundle folder. So the build itself still needs no network once it has the folder, and tests build the small committed bundle.

## Risks

- **The lab's page models change after S9** (S10 adds reports' places, S12 removes the claim pages). The site builds against the small bundle's schemas, so a change shows as a failed build when the small bundle is cut again, not in production.
- **Search engines see every address move at once.** Redirects are permanent and the sitemap lists only new addresses from the first deployment.
- **A wrong join at volume.** The chooser's held-out precision is 0.90 on 28 cases. Decision 7 shows it; the operator removes a wrong pair with the lab's hold, and the next bundle drops its file.
- **On-request pages cost reads.** Cached a day per version; the existing rate limits cover the path.
